## Опис проєкту

Консольний застосунок `lab9-self-v11` (.NET 9) зі статичним класом `CollectionUtils`, який містить чотири узагальнені методи. Поведінку кожного методу задають через делегат:

| Метод | Делегат | Що робить | Аналог у .NET |
|---|---|---|---|
| `Map<TSource, TResult>` | `Func<TSource, TResult>` | перетворює кожен елемент | LINQ `Select` |
| `MaxBy<T, TKey>` | `Func<T, TKey>` (`TKey : IComparable<TKey>`) | знаходить елемент з найбільшим ключем | LINQ `MaxBy` |
| `Filter<T>` | `Predicate<T>` | залишає елементи, що задовольняють умову | LINQ `Where` |
| `ForEach<T>` | `Action<T>` | виконує дію для кожного елемента | `List<T>.ForEach` |

Файли:
- `CollectionUtils.cs` — реалізація методів;
- `Product.cs` — клас товару для демонстрації;
- `Program.cs` — демонстрація на трьох колекціях: `List<int>`, `List<string>`, `List<Product>`.

Запуск:

## Звіт

### 1. Чому делегати корисні для створення таких утиліт?

Делегат дозволяє передати в метод **не дані, а поведінку**, тобто функцію. Завдяки цьому метод розділяється на дві частини:
- **незмінна частина** — алгоритм обходу колекції (`foreach`, збирання результату, пошук максимуму). Її написано один раз у `CollectionUtils`;
- **змінна частина** — що саме зробити з елементом. Її передають ззовні через делегат.

Тому один метод `Filter` відбирає і парні числа, і слова, довші за 4 літери, і товари, дорожчі за 1000 грн. Без делегатів довелося б писати окремий метод для кожної умови: `FilterEven`, `FilterLongWords`, `FilterExpensive` тощо.

Поєднання **generic-методів** і делегатів дає ще більше: методи працюють з будь-яким типом (`int`, `string`, `Product`), а компілятор перевіряє типи. Наприклад, у `Filter<Product>` неможливо передати умову для `string`.

Делегат можна зберегти у змінну і використати повторно. У програмі умова `Predicate<int> isEven = n => n % 2 == 0` використана двічі: у `Filter` і всередині `ForEach`.

У .NET є готові типи делегатів, тож свої оголошувати не потрібно:
- `Func<T, TResult>` — приймає елемент і повертає результат (`Map`, `MaxBy`);
- `Predicate<T>` — приймає елемент і повертає `bool` (`Filter`);
- `Action<T>` — приймає елемент і нічого не повертає (`ForEach`).

### 2. Як лямбда-вирази спрощують виклик цих методів?

Лямбда-вираз — це коротка анонімна функція, написана прямо в місці виклику. Без лямбд для кожної умови довелося б оголосити окремий іменований метод:

```csharp
static bool IsExpensive(Product p)
{
    return p.Price > 1000;
}
...
var expensive = CollectionUtils.Filter(products, IsExpensive);
```

З лямбдою той самий виклик займає один рядок, і умову видно одразу:

```csharp
var expensive = CollectionUtils.Filter(products, p => p.Price > 1000);
```

Переваги лямбд:
- **коротко й наочно:** логіка записана там, де використовується;
- **виведення типів:** у `p => p.Price` не треба вказувати, що `p` — це `Product`, компілятор сам бере тип з колекції. Так само він сам визначає `TResult` у `Map` (`Map(products, p => p.Name)` повертає колекцію `string`);
- **замикання (closure):** лямбда може використовувати змінні, оголошені поза нею. У програмі лямбда в `ForEach` змінює зовнішню змінну `index++`, щоб пронумерувати список фруктів;
- **легко міняти поведінку:** щоб знайти найдовше слово замість останнього за алфавітом, досить змінити лямбду з `f => f` на `f => f.Length`. Сам метод `MaxBy` не змінюється.

### 3. Порівняння власних методів з LINQ

| Власний метод | Вбудований аналог | Однаково | Відмінності |
|---|---|---|---|
| `CollectionUtils.Map` | `Enumerable.Select` | перетворює кожен елемент функцією | наш метод одразу будує `List`, LINQ працює ліниво |
| `CollectionUtils.Filter` | `Enumerable.Where` | відбирає елементи за умовою | наш приймає `Predicate<T>`, LINQ — `Func<T, bool>`; LINQ ліниво |
| `CollectionUtils.MaxBy` | `Enumerable.MaxBy` (.NET 6+) | шукає елемент з максимальним ключем | наш вимагає `IComparable<TKey>`, LINQ приймає ще й власний `IComparer` |
| `CollectionUtils.ForEach` | `List<T>.ForEach` | виконує дію для кожного елемента | у LINQ немає `ForEach` для `IEnumerable<T>`; наш працює з будь-якою колекцією |

Результати однакові. У розділі «Порівняння з LINQ» вивід `Map` і `Select`, `Filter` і `Where`, нашого `MaxBy` і LINQ `MaxBy` збігається.

Головні відмінності:
1. **Ліниве (відкладене) виконання.** LINQ `Select` і `Where` нічого не обчислюють, доки результат не почнуть перебирати, і не створюють проміжний список. Наші методи одразу проходять усю колекцію і повертають готовий `List`. Це простіше для розуміння, але займає більше пам'яті на великих даних.
2. **Методи розширення і ланцюжки.** LINQ-методи викликаються через крапку й легко з'єднуються в ланцюжок: `products.Where(p => p.Price > 1000).Select(p => p.Name)`. Наші методи звичайні статичні, тому виклики доводиться вкладати один в одного: `CollectionUtils.Map(CollectionUtils.Filter(...), ...)`. Якщо додати `this` до першого параметра, вони теж стануть методами розширення.
3. **Порожня колекція.** Наш `MaxBy` для порожньої колекції завжди викидає `InvalidOperationException`. LINQ `MaxBy` робить так для типів-значень, а для посилальних типів повертає `null`.
4. **Оптимізація і перевірка.** LINQ — частина .NET: він добре протестований і має оптимізації для масивів і списків. Для реальних проєктів варто використовувати саме його.

### Висновки

Делегати дозволяють написати алгоритм один раз, а поведінку передавати ззовні. Лямбда-вирази роблять передачу цієї поведінки короткою й зрозумілою. Разом з generic-методами це дає універсальні утиліти, які працюють з будь-якими типами даних. Власні `Map`, `Filter`, `MaxBy` і `ForEach` працюють так само, як `Select`, `Where`, `MaxBy` з LINQ, і це добре показує, як LINQ влаштований усередині. На практиці краще користуватися LINQ, а власні утиліти писати тоді, коли потрібна поведінка, якої в LINQ немає, або для навчання.
