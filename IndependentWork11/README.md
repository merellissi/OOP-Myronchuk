Консольний застосунок `IndependentWork11` (.NET 9): аналітика продажів за допомогою LINQ-пайплайнів з вимірюванням часу виконання.

Запуск:
```bash
dotnet run --project IndependentWork11 -c Release
```

## 1. Модель даних і тестові дані (Extract)

| Сутність | Поля | Кількість |
|---|---|---:|
| `Product` | `Id`, `Name`, `Category`, `UnitPrice` | 60 (6 категорій × 10 товарів) |
| `Customer` | `Id`, `Name`, `City` | 80 (8 міст) |
| `Sale` | `Id`, `ProductId`, `Quantity`, `SaleDate`, `CustomerId` | 1000 (01.01.2025 – 30.06.2026) |

`Sale` містить лише посилання на товар і клієнта (`ProductId`, `CustomerId`), як у реляційній базі даних, тому для аналітики потрібне об'єднання (`Join`).

Дані генерує клас `DataGenerator`:
- `Random` з фіксованим seed (2026), тому при кожному запуску дані однакові й результати можна відтворити;
- ціни товарів випадкові в реалістичних межах для кожної категорії (продукти 40–600 грн, електроніка 300–40 000 грн);
- кожен товар має випадкову «популярність» (вагу від 1 до 10), тому одні товари продаються частіше за інші, як у реальному магазині.

## 2. Опис пайплайнів (Transform)

Усі пайплайни реалізовані як окремі методи класу `SalesPipelines`, тому `Program.cs` лишається коротким. Кожен метод закінчується `.ToList()`. LINQ виконується ліниво, і без `ToList()` метод повернув би лише опис запиту, а `Stopwatch` виміряв би час створення запиту, а не його виконання.

### Пайплайн 1. Найпопулярніші продукти за категоріями — `TopProductsByCategory`

**Мета:** для кожної категорії знайти 3 товари з найбільшою кількістю проданих одиниць.

```
GroupBy(ProductId) → Select(Sum(Quantity)) → Join(products) → GroupBy(Category)
  → у кожній групі: OrderByDescending(Quantity) → ThenBy(Name) → Take(3)
  → OrderBy(Category)
```

| Оператор | Навіщо |
|---|---|
| `GroupBy(s => s.ProductId)` + `Sum` | зібрати всі продажі одного товару і порахувати загальну кількість |
| `Join` з `products` | отримати назву й категорію товару за `ProductId` |
| `GroupBy(x => x.Category)` | розбити товари на категорії |
| `OrderByDescending` + `Take(3)` | у кожній категорії взяти 3 найпопулярніші |
| `ThenBy(Name)` | однозначний порядок при однаковій кількості (у категорії «Одяг» Рукавички і Шарф мають по 106 шт.) |

Агрегування (`GroupBy` + `Sum`) виконується **до** `Join`, тому з'єднуються лише 60 підсумкових рядків, а не 1000 продажів.

### Пайплайн 2. Загальний дохід за містами клієнтів — `RevenueByCity`

**Мета:** визначити, клієнти з якого міста приносять найбільше доходу.

```
Join(products) → Join(customers) → Select(Quantity * UnitPrice) → GroupBy(City)
  → Select(Count, Sum) → OrderByDescending(Revenue)
```

| Оператор | Навіщо |
|---|---|
| перший `Join` з `products` | отримати `UnitPrice` і порахувати дохід продажу `Quantity * UnitPrice` |
| другий `Join` з `customers` | отримати місто клієнта |
| `GroupBy(x => x.City)` + `Sum`, `Count` | загальний дохід і кількість продажів кожного міста |
| `OrderByDescending(Revenue)` | спершу найприбутковіші міста |

### Пайплайн 3. Продажі за місяцями та роками — `SalesByMonth`

**Мета:** побачити динаміку продажів у часі.

```
Join(products) → GroupBy(new { Year, Month }) → Select(Count, Sum(Quantity), Sum(Revenue))
  → OrderBy(Year) → ThenBy(Month)
```

| Оператор | Навіщо |
|---|---|
| `Join` з `products` | ціна потрібна для обчислення доходу |
| `GroupBy(x => new { x.SaleDate.Year, x.SaleDate.Month })` | **складений ключ**: групування одночасно за роком і місяцем, щоб січень 2025 і січень 2026 були різними групами |
| `Sum(Quantity)`, `Sum(Revenue)` | кількість одиниць і дохід за місяць |
| `OrderBy(Year)` + `ThenBy(Month)` | хронологічний порядок |

### Пайплайн 4 (додатковий). Топ-5 клієнтів — `TopCustomers`

**Мета:** знайти найцінніших клієнтів: кількість покупок, загальна сума, середній чек і улюблена категорія.

```
Join(products) → GroupBy(CustomerId) → Select(Count, Sum, вкладений GroupBy(Category))
  → OrderByDescending(TotalSpent) → Take(5) → Join(customers)
```

Використано 6 різних операторів (`Join`, `GroupBy`, `Select`, `OrderByDescending`, `Take`, `First`). Улюблена категорія обчислюється **вкладеним** `GroupBy` всередині групи кожного клієнта: категорія, на яку клієнт витратив найбільше. `Join` з клієнтами виконується **після** `Take(5)`, тож дані підтягуються лише для 5 клієнтів, а не для всіх 80.

### Перевірка коректності

Пайплайни 2 і 3 групують ті самі продажі по-різному, тому загальні суми мають збігатися:
- дохід за містами = дохід за місяцями = **47 918 720,12 грн** → OK;
- кількість одиниць у пайплайні 3 = сума `Quantity` усіх продажів = **5511** → OK.

**Пайплайн 1.** Найпопулярніші товари за кількістю: Лампа (240 шт.), Футболка (219 шт.), Клавіатура (198 шт.). У категорії «Книги» продажі найменші (лідер — Енциклопедія, 126 шт.).

**Пайплайн 2.** Найбільше доходу дають Київ (9,48 млн грн) і Одеса (8,05 млн грн), найменше — Житомир (2,95 млн грн). Дохід міста здебільшого визначає кількість продажів: у Києві їх 200, у Житомирі 57. Але не завжди: Луцьк при 83 продажах обійшов Львів (119 продажів), бо клієнти з Луцька купували дорожчі товари.

**Пайплайн 3.** Щомісяця 45–64 продажі на 1,9–4,0 млн грн. Найприбутковіший місяць — липень 2025 (3,98 млн грн), найменш прибутковий — травень 2025 (1,87 млн грн).

**Пайплайн 4.** У всіх п'яти найкращих клієнтів улюблена категорія — **Електроніка**. Вона найдорожча (до 40 000 грн за одиницю), тому кілька покупок електроніки дають більшу суму, ніж багато дешевих товарів.

## 4. Вимірювання продуктивності

Для кожного пайплайну створюється **новий `Stopwatch`**. Вимірюються:
- **перший запуск** — разом із JIT-компіляцією;
- **середній час** зі 100 наступних запусків.

Програма запущена в конфігурації Release.

| Пайплайн | Перший запуск, мс | Середній, мс | Оператори |
|---|---:|---:|---|
| 1. Топ-3 продукти за категоріями | 31,549 | 0,942 | GroupBy, Sum, Join, GroupBy, OrderBy, Take |
| 2. Дохід за містами | 17,793 | 0,963 | Join, Join, GroupBy, Sum, OrderBy |
| 3. Продажі за місяцями | 6,123 | **0,752** | Join, GroupBy, Sum, OrderBy, ThenBy |
| 4. Топ-5 клієнтів | 5,607 | **1,224** | Join, GroupBy, вкладений GroupBy, OrderBy, Take, Join |

### Аналіз результатів

1. **Перший запуск у 4,5–33 рази повільніший за наступні.** Під час першого виклику .NET компілює код методів у машинний (JIT), створює внутрішні типи для анонімних об'єктів і generic-методів LINQ (`GroupBy`, `Join` з конкретними типами), завантажує потрібні частини бібліотек. Повторні запуски використовують уже скомпільований код.
2. **Найдовший перший запуск у пайплайна 1 (31,5 мс)**, бо він виконується першим і «оплачує» JIT для спільної інфраструктури LINQ (`GroupBy`, `Join`, `Sum`, `OrderBy`). Кожен наступний пайплайн запускається швидше (17,8 → 6,1 → 5,6 мс), бо частина коду вже скомпільована. Отже, час першого запуску залежить не так від складності пайплайну, як від порядку виконання.
3. **Після «прогріву» всі пайплайни обробляють 1000 продажів приблизно за 1 мс.** Відмінності між ними пояснюються кількістю роботи:
   - **пайплайн 3 найшвидший (0,75 мс):** лише один `Join`, а групування дає всього 18 груп;
   - **пайплайн 2 (0,96 мс):** два `Join`, тобто дві хеш-таблиці й удвічі більше проміжних об'єктів;
   - **пайплайн 1 (0,94 мс):** два `GroupBy` і сортування всередині кожної категорії, але `Join` працює лише з 60 підсумковими рядками;
   - **пайплайн 4 найповільніший (1,22 мс):** для кожного з 80 клієнтів виконується ще одне вкладене групування за категоріями й сортування.

### Фактори, що впливають на час виконання

- **JIT-компіляція:** перший запуск завжди повільніший (див. вище).
- **Кількість `Join` і `GroupBy`:** кожен із них будує хеш-таблицю (`Join` — для другої колекції, `GroupBy` — для груп). Це O(n) за часом, але з виділенням пам'яті.
- **Порядок операторів:** фільтрування й агрегування до `Join` зменшують обсяг даних для з'єднання (пайплайн 1 агрегує до `Join`, пайплайн 4 робить `Join` з клієнтами після `Take(5)`).
- **Вкладені запити:** вкладений `GroupBy` у пайплайні 4 виконується для кожної групи, тому пайплайн найдорожчий.
- **Створення проміжних об'єктів:** кожен `Select` / `Join` створює нові анонімні об'єкти, що навантажує збирач сміття (GC).
- **Тип `decimal`:** обчислення з `decimal` точні (важливо для грошей), але повільніші за `double`.
- **Конфігурація збірки:** у Debug код не оптимізований і виконується повільніше, тому вимірювання робилися в Release.
- **Фонові процеси та точність таймера:** на часах близько 1 мс помітно впливає завантаження системи, тому береться середнє зі 100 запусків.

## 5. Висновки

- **LINQ добре підходить для ETL та аналітики.** Пайплайн читається як опис задачі: «з'єднати → згрупувати → порахувати → відсортувати», і майже дослівно відповідає SQL-запиту (`JOIN`, `GROUP BY`, `SUM`, `ORDER BY`). Та сама логіка на циклах `foreach` потребувала б кількох словників, вкладених циклів і ручного сортування, тобто в кілька разів більше коду й більше місць для помилок.
- **Продуктивність достатня:** після прогріву кожен пайплайн обробляє 1000 продажів приблизно за 1 мс. Для звітів і аналітики на тисячах і десятках тисяч записів цього більш ніж достатньо.
- **Важливо пам'ятати про ліниве виконання:** без `ToList()` запит виконується лише під час перебору результату, і якщо результат перебрати кілька разів, запит виконається кілька разів.
- **Для великих обсягів даних** (мільйони записів) варто агрегувати якомога раніше, не повторювати однакові `Join` у різних пайплайнах (наприклад, один раз з'єднати продажі з товарами і використати результат кілька разів), використовувати `Dictionary` для частих пошуків, PLINQ (`AsParallel()`) для паралельної обробки або переносити обчислення в базу даних.
- **Для читабельності** кожен пайплайн винесено в окремий метод з промовистою назвою, кожен крок прокоментовано, а результати оформлено як `record`. Коректність перевіряється порівнянням підсумків різних пайплайнів.
