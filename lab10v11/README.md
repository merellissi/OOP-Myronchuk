## 1. Сутності та тестові дані

```csharp
public class Event { public int Id; public string Name; public DateTime Date; public int LocationId; }
public class Venue { public int Id; public string Name; public int Capacity; }
```

`Event.LocationId` посилається на `Venue.Id`. Назви й місткості локації в події немає, тому для запитів 1–3 потрібне об'єднання (join). Результати запитів оформлено як `record` (`EventAtVenue`, `EventVenuePair`, `VenueEventCount`). Записи порівнюються за значенням, тому програма автоматично перевіряє, що обидва синтаксиси дали однаковий результат (`SequenceEqual`).

**Тестові дані:** 10 локацій (місткість від 120 до 4500 місць) і 20 подій з грудня 2023 до квітня 2027 року. Дані підібрано так, щоб перевірити кожен запит:
- у 2024 році 6 подій, з них 2 на малих локаціях: «Джазовий вечір» (450 місць) і «Хакатон OOP» (400 місць). Запит 1 має їх відсіяти;
- «Коворкінг «Hub»» не має жодної події: перевірка, що запит 3 показує локації з нулем подій;
- є минулі й майбутні події, тож запит 4 має що шукати.

**Великий набір** для вимірювань: 1 000 локацій і 100 000 подій з випадковими датами 2023–2027 років. `Random` з фіксованим seed, тому дані однакові при кожному запуску.

## 2. Запити

### Запит 1. Події 2024 року на локаціях з місткістю > 500 (фільтрація + join)

Синтаксис запитів:
```csharp
from e in events
join v in venues on e.LocationId equals v.Id
where e.Date.Year == 2024 && v.Capacity > 500
orderby e.Date
select new EventAtVenue(e.Name, e.Date, v.Name, v.Capacity)
```

Синтаксис методів:
```csharp
events.Join(venues, e => e.LocationId, v => v.Id, (e, v) => new { e, v })
      .Where(x => x.e.Date.Year == 2024 && x.v.Capacity > 500)
      .OrderBy(x => x.e.Date)
      .Select(x => new EventAtVenue(x.e.Name, x.e.Date, x.v.Name, x.v.Capacity))
```

**Результат:** 4 події — IT Conference Rivne (Стадіон «Авангард», 4500), Концерт гурту «Антитіла» (Stereo Plaza, 3000), Опера «Наталка Полтавка» (Львівська опера, 1100), Новорічний бал (Палац «Україна», 3700). «Джазовий вечір» і «Хакатон OOP» відсіяно за місткістю, «Stand-up шоу» — за роком (2023).

### Запит 2. Події разом з локаціями (join)

Синтаксис запитів:
```csharp
from e in events
join v in venues on e.LocationId equals v.Id
orderby e.Id
select new EventVenuePair(e.Id, e.Name, v.Name)
```

Синтаксис методів:
```csharp
events.Join(venues, e => e.LocationId, v => v.Id, (e, v) => new EventVenuePair(e.Id, e.Name, v.Name))
      .OrderBy(p => p.EventId)
```

**Результат:** 20 пар «назва події → назва локації».

### Запит 3. Кількість подій для кожної локації (GroupJoin + Count)

Синтаксис запитів:
```csharp
from v in venues
join e in events on v.Id equals e.LocationId into venueEvents
let count = venueEvents.Count()
orderby count descending, v.Name
select new VenueEventCount(v.Name, count)
```

Синтаксис методів:
```csharp
venues.GroupJoin(events, v => v.Id, e => e.LocationId,
                 (v, venueEvents) => new VenueEventCount(v.Name, venueEvents.Count()))
      .OrderByDescending(x => x.EventCount)
      .ThenBy(x => x.VenueName)
```

Використано **`GroupJoin`** (`join … into`), а не `GroupBy` за подіями: `GroupJoin` повертає кожну локацію з групою її подій, навіть порожньою, тоді як `GroupBy` за `LocationId` не побачив би локацію без подій.

**Результат:** Стадіон «Авангард» — 4, Мистецький Арсенал — 3, шість локацій по 2, Луцький будинок культури — 1, **Коворкінг «Hub» — 0**. Сума — 20 подій.

### Запит 4. Подія з найближчою датою

«Найближча» трактується як найближча **майбутня** подія відносно поточної дати (`DateTime.Today`).

Синтаксис запитів (у ньому немає `MinBy`, тому сортування + перший елемент):
```csharp
(from e in events
 where e.Date >= today
 orderby e.Date
 select e).FirstOrDefault()
```

Синтаксис методів:
```csharp
events.Where(e => e.Date >= today)
      .MinBy(e => e.Date)
```

**Результат** (запуск 14.11.2026): **Рок-фестиваль**, 21.11.2026, Stereo Plaza (через 7 днів). Якщо майбутніх подій немає, обидва варіанти повертають `null`.

**Перевірка:** для всіх чотирьох запитів синтаксис запитів і синтаксис методів дали однаковий результат.

## 3. Час виконання (Stopwatch)

Для кожного запиту і кожного синтаксису створюється новий `Stopwatch`. Кожен метод закінчується `ToList()` / `FirstOrDefault()` / `MinBy()`, щоб запит виконався, а не лише створився (відкладене виконання). Вимірюються **перший запуск** (разом із JIT-компіляцією) і **середній час** повторних запусків. Конфігурація — **Release**.

## 4. Аналіз і висновки

**Перший запуск і JIT.** На тестових даних перший запуск у 30–5700 разів повільніший за наступні. Найдовший — перший запит (108 мс): він першим використовує LINQ, і .NET у цей момент компілює (JIT) методи `Join`, `Where`, `OrderBy`, створює внутрішні типи для анонімних об'єктів і завантажує потрібні бібліотеки. Наступні запити вже використовують частину скомпільованого коду, тому їхній перший запуск займає 1–7 мс. Для порівняння швидкості треба дивитися на середній час, а не на перший запуск.

**Тестові дані (20 подій).** Після прогріву всі запити виконуються за 2–31 мкс. Різниця між синтаксисами тут випадкова: у запиті 1 швидший синтаксис запитів (18,9 проти 31,5 мкс), а в запиті 3 — синтаксис методів (18,3 проти 27,5 мкс). На такому малому обсязі час визначають не самі операції, а накладні витрати й фонові процеси. Висновки про ефективність на 20 елементах робити не можна, тому виміри повторено на 100 000 подій.

**Найдорожчі операції (великий набір):**
1. **`Join` з великим результатом (запит 2, 45–64 мс) — найдорожчий.** `Join` будує хеш-таблицю для локацій, проходить усі 100 000 подій, створює 100 000 нових об'єктів-результатів, а потім `OrderBy` сортує їх (O(n log n)).
2. **Фільтр + join (запит 1, 38–43 мс)** майже такий самий дорогий, хоча результат набагато менший. `Where` стоїть **після** `Join`, тому об'єднання виконується для всіх 100 000 подій, а відкидаються вони вже потім. Оптимізація: спершу відфільтрувати події за роком, а вже потім робити `Join`, тоді об'єднуватиметься приблизно в 5 разів менше елементів.
3. **`GroupJoin` + `Count` (запит 3, 7,5–11,8 мс)** у 5–6 разів дешевший за `Join`, хоча теж обробляє всі події. Результат — лише 1 000 рядків (по одному на локацію), і сортувати треба 1 000 елементів, а не 100 000.
4. **Пошук найближчої події (запит 4, ~2,4 мс) — найдешевший:** один прохід списку без створення нових об'єктів. `OrderBy(...).FirstOrDefault()` працює так само швидко, як `MinBy`: .NET розпізнає комбінацію `OrderBy` + `First` і замість повного сортування шукає мінімум за один прохід.

**Синтаксис запитів vs синтаксис методів.** Компілятор перетворює синтаксис запитів на виклики методів, тому сам вибір синтаксису на швидкість не впливає. У запитах 2 і 3 синтаксис запитів повільніший (64 проти 45 мс і 12 проти 7,5 мс), бо `orderby` перед `select` і `let` змушують компілятор створювати проміжний анонімний об'єкт для кожного елемента, а в синтаксисі методів результат створюється одразу в `Join` / `GroupJoin`. Швидкість визначає структура ланцюжка, а не синтаксис.

**Інші спостереження.** Інколи перший запуск на великому наборі швидший за середній (запит 2, синтаксис методів: 27,6 проти 44,8 мс). Кожен запуск створює сотні тисяч об'єктів, і під час повторних запусків спрацьовує збирач сміття (GC), паузи якого потрапляють у середній час.

**Підсумок:**
- найдорожчі — операції, що **створюють багато нових об'єктів і сортують великі обсяги** (`Join` з повним результатом + `OrderBy`);
- **агрегація** (`Count`, `GroupJoin`) і **один прохід** (`MinBy`, `Where` + `First`) значно дешевші;
- **фільтрувати варто якомога раніше**, до `Join` і сортування;
- синтаксис запитів зручний для `join` і складних умов, синтаксис методів коротший і дає доступ до `MinBy`, `Take`, `Any`. Швидкість у них однакова за однакової структури запиту.
