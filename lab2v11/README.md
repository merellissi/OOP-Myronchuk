# Лабораторна робота №2

**Тема:** Клас із кількома конструкторами. Життєвий цикл об'єкта.

**Варіант:** 11 (клас `Plane`)

## Мета

Навчитися реалізовувати перевантажені конструктори, дослідити порядок їх викликів та зрозуміти основи життєвого циклу об'єкта в C#.

## Що реалізовано

Клас `Plane` (літак) має:

- приватні поля `_airline`, `_model`, `_capacity`;
- публічні властивості `Airline`, `Model`, `Capacity` (для `Capacity` є валідація: місткість повинна бути більшою за 0);
- параметризований конструктор `Plane(airline, model, capacity)`;
- конструктор за замовчуванням, який викликає параметризований через `: this("N/A", "Boeing 737", 150)`;
- метод `Fly()`, що виводить повідомлення про політ;
- деструктор `~Plane()`, що виводить повідомлення про знищення об'єкта.

У `Program.cs` створюються три об'єкти різними конструкторами, викликаються їхні методи, перевіряється валідація, а наприкінці примусово запускається збирач сміття (`GC.Collect()` та `GC.WaitForPendingFinalizers()`).

## Запуск

```
dotnet run
```



## Висновок

Під час виконання роботи я реалізувала клас `Plane` з приватними полями, властивостями (з валідацією місткості), двома перевантаженими конструкторами та деструктором. Конструктор за замовчуванням викликає параметризований через `: this()`, що усуває дублювання коду ініціалізації.

Я дослідила життєвий цикл об'єкта: об'єкт створюється оператором `new`, який виділяє пам'ять у купі та викликає конструктор. Об'єкт існує, доки на нього є хоча б одне посилання. Коли посилань не залишається, збирач сміття викликає деструктор і звільняє пам'ять. Під час роботи з'ясувалося, що об'єкти, створені безпосередньо в `Main`, можуть не знищуватися при `GC.Collect()`, тому створення об'єктів було винесено в окремий метод. Момент виклику деструктора визначає збирач сміття, а не програміст, а порядок знищення об'єктів не гарантований. Тому `GC.Collect()` вручну використовується лише в навчальних цілях.
