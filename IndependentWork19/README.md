## 1. Власний тип винятку `OutOfStockException`

Виняток сигналізує, що на складі недостатньо товару для замовлення.

```csharp
public class OutOfStockException : Exception
{
    public string? ProductName { get; }
    public int RequestedQuantity { get; }
    public int AvailableQuantity { get; }
    public int Shortage => RequestedQuantity - AvailableQuantity;

    public OutOfStockException() : base("Товару недостатньо на складі.") { }
    public OutOfStockException(string message) : base(message) { }
    public OutOfStockException(string message, Exception innerException) : base(message, innerException) { }

    public OutOfStockException(string message, string productName, int requestedQuantity, int availableQuantity)
        : base(message) { ... }
}
```

- **Три стандартні конструктори:** без параметрів, з `message`, з `message` + `innerException`. Останній дозволяє зберегти причину помилки: у демонстрації це `TimeoutException("Склад не відповів за 5 с")`.
- **Додаткові властивості** (`ProductName`, `RequestedQuantity`, `AvailableQuantity`, `Shortage`) дають обробнику повний контекст. Без них довелося б розбирати текст повідомлення.
- Назва закінчується на `Exception`, клас успадковує `System.Exception`.

### Демонстрація з `try-catch-finally`

Метод `Warehouse.Reserve` кидає три різні винятки. У `Program.cs` вони обробляються блоками `catch` від найбільш специфічного до загального:

```csharp
try
{
    warehouse.Reserve(product, quantity);
}
catch (OutOfStockException ex) when (ex.AvailableQuantity > 0)  // товар частково є
{
    // пропонуємо часткове замовлення
}
catch (OutOfStockException ex)          // товару немає зовсім
catch (ArgumentOutOfRangeException ex)  // некоректна кількість
catch (Exception ex)                    // усе інше (тут — KeyNotFoundException)
finally
{
    // виконується завжди
}
```

Результат (склад: Ноутбук — 3, Мишка — 10, Монітор — 0):

| Замовлення | Що сталося |
|---|---|
| Ноутбук × 2 | успіх, залишок 1 шт. |
| Ноутбук × 5 | `OutOfStockException` з фільтром `when`: є 1, бракує 4 → пропозиція часткового замовлення |
| Монітор × 1 | `OutOfStockException` без фільтра: товару немає зовсім |
| Мишка × 0 | `ArgumentOutOfRangeException` |
| Планшет × 1 | `KeyNotFoundException` → загальний `catch (Exception)` |

`finally` виконався в усіх п'яти випадках. Фільтр `when` дозволив по-різному обробити той самий тип винятку залежно від його властивостей.

## 2. Коли кидати виняток, а коли повертати `Result<T>`

**Виняток** варто кидати, коли метод **не може виконати свій контракт** і ситуація справді виняткова: розірвалося з'єднання з БД, не знайдено конфігураційний файл, у метод передано некоректні аргументи (помилка програміста). Виняток неможливо випадково проігнорувати, він несе стек викликів і сам «піднімається» до місця, де його можна обробити. Але він повільніший за звичайне повернення значення (розкрутка стека), і його легко «проковтнути» порожнім `catch`. **`Result<T>`** (а також `bool TryXxx(out ...)`, `null`) варто повертати для **очікуваних неуспіхів**, які є нормальною частиною бізнес-логіки: валідація введення, пошук запису, якого може не бути, перевірка залишку на складі. Такий результат видно прямо в сигнатурі методу, обробка йде звичайним `if` без `try-catch`, і це швидше. Недолік — результат можна забути перевірити. У нашому проєкті є обидва варіанти: `Reserve` кидає `OutOfStockException`, бо після його виклику товар **гарантовано** зарезервований, а `TryReserve` повертає `Result<int>`, бо нестача товару в інтернет-магазині — звичайна ситуація, яку краще обробити як відповідь, а не як аварію. Частина 2 демонстрації показує, що ті самі 5 замовлень з `Result<T>` обробляються простим циклом без жодного `try-catch`. **Правило:** якщо операція може закономірно «не спрацювати» — `Result`, якщо ситуація справді виняткова — виняток.

## 3. Сценарії Polly

Усі пайплайни створено через актуальний API **`ResiliencePipelineBuilder`** (Polly v8). Кожна стратегія логує свої події (`OnRetry`, `OnOpened`, `OnHalfOpened`, `OnClosed`, `OnTimeout`, `OnFallback`), а імітації сервісів логують кожен виклик.

### Сценарій 1. Оплата замовлення — Retry + exponential backoff + jitter

**Проблема.** Платіжний шлюз під навантаженням іноді відповідає `503 Service Unavailable`. Збій короткочасний: через долю секунди той самий запит, найімовірніше, пройде. Показувати клієнту помилку оплати через такий збій погано.

**Обрана стратегія — Retry**, бо збій тимчасовий і повтор має шанс на успіх:
- `MaxRetryAttempts = 3`: максимум 4 спроби, щоб не змушувати клієнта чекати безкінечно;
- `BackoffType = Exponential`, `Delay = 0,5 с`: затримки ростуть, і перевантажений шлюз має час відновитися;
- `UseJitter = true`: випадкова складова затримки. Якщо сотні клієнтів отримали 503 одночасно, без jitter вони повторили б запити теж одночасно й знову перевантажили б шлюз («шторм повторів»);
- `ShouldHandle = Handle<HttpRequestException>()`: повторюємо **лише** мережеві збої. Помилка валідації постійна, і повтор нічого не змінить;
- **ідемпотентність:** кожна спроба передає той самий ключ `order-1001`. Оплата — неідемпотентна операція: якщо шлюз списав гроші, але відповідь загубилась, повтор без ключа списав би їх удруге. Ключ дозволяє шлюзу розпізнати повтор.

```csharp
ResiliencePipeline pipeline = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<HttpRequestException>(),
        MaxRetryAttempts = 3,
        Delay = TimeSpan.FromMilliseconds(500),
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true,
        OnRetry = args =>
        {
            Log.Write($"Retry #{args.AttemptNumber + 1} через {args.RetryDelay.TotalSeconds:F2} с. Причина: {args.Outcome.Exception?.Message}");
            return default;
        }
    })
    .Build();

string transaction = await pipeline.ExecuteAsync(
    async token => await gateway.ChargeAsync(amount, orderKey, token), CancellationToken.None);
```

**Опис виводу:**
- **1а** (шлюз двічі відповідає 503): дві невдалі спроби, Retry #1 через 0,18 с, Retry #2 через 0,52 с, **третя спроба успішна** (0,95 с від початку). Клієнт не побачив жодної помилки.
- **1б** (шлюз «лежить» довго): 4 спроби із затримками 0,58 → 0,14 → 0,96 с, після чого Polly прокидає останній виняток → «ОСТАТОЧНА НЕВДАЧА після 4 викликів» (1,96 с). Retry обмежений, і програма не «зависає».
- **1в** (сума −5 грн): `ArgumentException`, **жодного повтору** і жодного виклику шлюзу, бо `ShouldHandle` не реагує на помилки валідації.

**Про затримки.** Затримки не завжди ростуть (у 1б: 0,58 → 0,14 → 0,96 с). Це не помилка: з `UseJitter = true` Polly v8 для експоненційної затримки використовує алгоритм *decorrelated jitter*. Окремі затримки випадкові, але в середньому зростають експоненційно, і повтори різних клієнтів не збігаються в часі.

### Сценарій 2. Статус доставки — Circuit Breaker

**Проблема.** Сервіс доставки повністю впав (тут — на 2 с). Retry тут шкідливий: кожен запит клієнта даремно чекає, а сервіс, який намагається піднятися, отримує ще більше запитів.

**Обрана стратегія — Circuit Breaker** («автоматичний вимикач»). Після серії помилок він припиняє звертатися до сервісу і миттєво відповідає помилкою, даючи сервісу час відновитися:
- `FailureRatio = 0.5`, `MinimumThroughput = 3`, `SamplingDuration = 5 с`: розімкнути ланцюг, якщо за останні 5 с ≥50% запитів невдалі (і запитів було щонайменше 3, щоб не реагувати на одну випадкову помилку);
- `BreakDuration = 1,5 с`: скільки часу ланцюг розімкнений;
- стани: **Closed** (запити проходять) → **Open** (запити відхиляються з `BrokenCircuitException`) → **Half-Open** (один пробний запит) → **Closed** (якщо пробний успішний) або знову **Open**.

```csharp
ResiliencePipeline pipeline = new ResiliencePipelineBuilder()
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<HttpRequestException>(),
        FailureRatio = 0.5,
        MinimumThroughput = 3,
        SamplingDuration = TimeSpan.FromSeconds(5),
        BreakDuration = TimeSpan.FromSeconds(1.5),
        OnOpened = args => { Log.Write($">>> Circuit OPEN на {args.BreakDuration.TotalSeconds:F1} с"); return default; },
        OnHalfOpened = args => { Log.Write(">>> Circuit HALF-OPEN"); return default; },
        OnClosed = args => { Log.Write(">>> Circuit CLOSED"); return default; }
    })
    .Build();
```

**Опис виводу** (запит кожні 0,4 с):

| Час | Запит | Стан ланцюга | Результат |
|---|---|---|---|
| 0,04 с | 1 | Closed | помилка сервісу |
| 0,47 с | 2 | Closed | помилка сервісу |
| 0,92 с | 3 | Closed → **Open** | помилка сервісу; 3 з 3 запитів невдалі (100% ≥ 50%) — ланцюг розімкнувся |
| 1,33–2,15 с | 4, 5, 6 | Open | **відхилено миттєво**, сервіс не викликався |
| 2,57 с | 7 | **Half-Open** → **Closed** | пробний запит успішний (сервіс уже відновився) |
| 3,04–3,92 с | 8–10 | Closed | успіх |

Підсумок: **10 запитів клієнта, лише 7 реальних викликів сервісу.** Три запити під час збою не навантажували сервіс і не змушували клієнта чекати: відмова була миттєвою. Після відновлення сервісу вимикач сам повернувся в нормальний режим.

### Сценарій 3. Курс валют — Fallback + Retry + Timeout

**Проблема.** Сервіс курсу валют іноді «зависає» і не відповідає секундами. Якщо чекати, сторінка товару не завантажиться. Курс, неточний на кілька копійок, кращий за помилку чи безкінечне очікування.

**Обрана стратегія — комбінація трьох:**
- **Timeout** (500 мс): кожна спроба обмежена в часі, тож завислий запит скасовується;
- **Retry** (2 повтори через 0,2 с): зависання може бути разовим;
- **Fallback**: якщо всі спроби невдалі, повертаємо кешований курс (41,10 грн) замість винятку.

**Порядок стратегій важливий:** перша додана — зовнішня, тобто `Fallback( Retry( Timeout( виклик ) ) )`. Тайм-аут обмежує **кожну** спробу окремо, Retry повторює спроби, що завершились тайм-аутом, а Fallback перехоплює остаточну невдачу. Якби Timeout стояв зовні Retry, він обмежував би загальний час усіх спроб разом.

```csharp
ResiliencePipeline<decimal> pipeline = new ResiliencePipelineBuilder<decimal>()
    .AddFallback(new FallbackStrategyOptions<decimal>
    {
        ShouldHandle = new PredicateBuilder<decimal>()
            .Handle<TimeoutRejectedException>()
            .Handle<HttpRequestException>(),
        FallbackAction = args => Outcome.FromResultAsValueTask(CachedRate)
    })
    .AddRetry(new RetryStrategyOptions<decimal>
    {
        ShouldHandle = new PredicateBuilder<decimal>().Handle<TimeoutRejectedException>(),
        MaxRetryAttempts = 2,
        Delay = TimeSpan.FromMilliseconds(200)
    })
    .AddTimeout(TimeSpan.FromMilliseconds(500))   // у коді — через TimeoutStrategyOptions з OnTimeout
    .Build();
```

**Опис виводу:**
- **3а** (сервіс відповідає за 100 мс): один виклик, курс **41,35 грн** за 0,14 с. Стратегії не втручались.
- **3б** (сервіс відповідає за 2 с): три спроби, кожна обірвана тайм-аутом рівно через ~0,5 с (0,51 / 1,25 / 1,97 с), між ними Retry з паузою 0,2 с. Після третього тайм-ауту спрацював **Fallback**, і користувач отримав кешований курс **41,10 грн** через 1,97 с замість очікування чи помилки.

## 4. Інші патерни: Bulkhead

**Bulkhead** («перегородка») обмежує кількість одночасних звернень до ресурсу, щоб збій одного сервісу не забрав усі потоки й з'єднання застосунку. Наприклад, якщо сервіс доставки повільний, а запитів до нього не більше 10 одночасно, решта функцій магазину продовжує працювати. У Polly v8 цей патерн реалізовано стратегією **Concurrency Limiter / Rate Limiter** (пакет `Polly.RateLimiting`). У цій роботі він не реалізовувався, бо для демонстрації потрібне справжнє паралельне навантаження.

## 5. Висновки щодо Polly

**Переваги:**
- **Декларативність:** політика описується налаштуваннями (кількість спроб, тип затримки, пороги), а не ручними циклами з `try-catch` і `Thread.Sleep`, як у прикладі з методички. Код виклику сервісу при цьому не змінюється, він просто загортається в `pipeline.ExecuteAsync(...)`.
- **Комбінування стратегій** в одному пайплайні (сценарій 3: Fallback + Retry + Timeout). Вручну таку логіку писати довго, і в ній легко помилитися.
- **Готові перевірені реалізації** складних алгоритмів: Circuit Breaker зі станами й статистикою у ковзному вікні, decorrelated jitter, кооперативний тайм-аут через `CancellationToken`.
- **Вибірковість:** `ShouldHandle` дозволяє реагувати лише на тимчасові помилки (сценарій 1в).
- **Спостережуваність:** callback-и (`OnRetry`, `OnOpened`, ...) дають місце для логування й метрик.
- Пайплайн створюється один раз і використовується повторно, а Circuit Breaker при цьому зберігає стан між викликами.

**Обмеження й ризики:**
- **Retry не виправляє постійні помилки** і лише затримує відповідь. Потрібно правильно налаштувати `ShouldHandle`.
- **Retry неідемпотентних операцій небезпечний:** повтор оплати може двічі списати гроші. Потрібні ключі ідемпотентності або інший захист.
- **Повтори збільшують навантаження** на сервіс, що й так має проблеми. Без backoff, jitter і обмеження кількості спроб Retry може погіршити ситуацію.
- **Тайм-аут працює лише з кодом, що підтримує `CancellationToken`.** Якщо операція ігнорує токен, Polly не зможе її перервати.
- **Порядок стратегій** у пайплайні суттєво впливає на поведінку, і помилка в порядку дає неочевидні наслідки.
- **Параметри треба підбирати** під реальний сервіс: занадто чутливий Circuit Breaker розмикатиметься через випадкові помилки, а занадто довгий Retry змусить користувача чекати.
- Polly — додаткова залежність і ще один рівень абстракції, який треба розуміти, щоб налагоджувати проблеми.

Загалом Polly дозволяє зробити роботу із зовнішніми сервісами надійною без складного ручного коду. Але це не «чарівна кнопка»: стратегію треба обирати під характер збою. Для короткочасних збоїв підходить Retry, для тривалої недоступності — Circuit Breaker, для повільних відповідей — Timeout, а Fallback — коли можлива прийнятна заміна результату.

===== Частина 2. Ті самі замовлення через Result<T> =====
Ноутбук × 2: OK, залишок 1 шт.
